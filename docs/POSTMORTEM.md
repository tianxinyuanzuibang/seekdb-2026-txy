## 2. 实现层面的坑（按发现顺序）

### 2.1 一开始就差点做错方向
第一反应是"改 SeekDB 源码"。靠查官方提交 diff（300 个文件全删除）才确认是从零实现。**教训：用可核对的证据判定题目性质，别按文档字面猜。**

### 2.2 一次性引入的三个 bug 被"测试全绿"掩盖（差点 0 分上线）
- `_expr_name` 函数头被性能重构覆盖，函数体变成 `return` 后的死代码 → 任何无别名投影 `NameError`
- `ORDER BY distance`（投影别名，赛题 2.2 示例的写法）解析不到
- 引号向量 `'[0, 2]'`（赛题示例+官方用例的写法）被当字符串拒绝

**为什么 185 个测试全绿？** 因为我们自己的用例只用裸向量 `[0,0,0]`、只按完整表达式排序。**测试集被官方样例的形态带偏了。**
**怎么发现**：把官方公开用例接进来跑，`vector_euclidean` 直接失败。
**教训：自建测试必须刻意覆盖"样例没用过的形态"，最好直接用对方的断言格式反测。**

### 2.3 形态审计穷举出的 5 个语义 bug
对官方用例未覆盖的 35 类形态逐一探针，抓到：
1. **UPDATE 非原子**：失败行之前的行已被改写（赛题明文禁止"语句失败留下部分修改"）→ 数据损坏级
2. **向量 TopK 忽略 `ORDER BY DESC`**（静默反向语义）
3. **无 LIMIT 的向量 TopK 返回空**（keep=0）
4. **`LIMIT 0` 崩溃**（`max() empty`）
5. **事务内向量检索看不到自己的插入**（根因在存储层：列扫描不合并事务 overlay）
6. 引号向量绕过维度/float32 校验（`'[1e39,2]'` 被接受）
7. 主键 UPDATE 静默匹配 0 行；嵌套 BEGIN 被接受

**教训：多行 INSERT 是原子的而 UPDATE 不是，说明"同类语义多处实现"必须逐一验证。**

### 2.4 语句边界扫描：两个连环 bug（最接近"全盘皆输"）
**Bug A — 多行语句被执行成多段**
```sql
create table t (
  id bigint primary key,
  v vector(2)
);
```
被按行切碎逐行执行，表建不出来。根因：快速扫描只数方括号（向量），不数圆括号（CREATE TABLE/函数参数）。官方 20 用例全是单行，所以测不到。**赛题 2.2 示例恰恰是多行的。**

**Bug B — 驱动指令 `--mode ann` 被切掉首字符**
指令边界被当分号切割，多消费一个 `-`，`-mode ann` 被当注释吞掉，模式切换失效。顺带发现 `set_mode` 里 `executor` 未定义（`NameError`）。

### 2.5 性能回归：三起，全部是"修 A 时引入 B"
1. 指令检测让每条批量 INSERT 走逐字符慢路径：250KB 语句 2.2ms→51ms（写入阶段 +5s）
2. **向量缓存永不建立（鸡生蛋）**：设计意图是"无缓存=超大表→流式"，但缓存本来就要靠首次查询填充 → 永远走流式 → 查询 12ms→83ms。**只有跑正式规模（10k×128）才暴露，本地小规模测不出。**
3. 修缓存时把 ANN 的候选子集当全表存进缓存 → recall 塌到 0.15、78 个契约违规

**教训：性能必须在"正式规模 + 空闲机器"上测。我们 Mac 负载 168 时测出的数字全是噪声，换到空闲 Linux 服务器才可信。**

### 2.6 崩溃模型与持久化（这块一次就做对了）
- 持久化点定在"COMMIT 响应发出前 fsync"，按批而不是按行
- WAL 长度+CRC 帧格式，残尾记录丢弃；恢复只认已提交前缀 → 天然幂等
- 6 个 SIGKILL 场景（含"恢复途中反复被杀"）全部通过
- 超内存场景：流式 TopK（2 万行×128 维，31.8 MiB 峰值）与暴力真值一致

### 2.7 工程杂项
- macOS 打包 tar 会带 `._*` AppleDouble 文件，服务器上被当测试用例扫进去（且不是合法 UTF-8）→ `tar --no-mac-metadata` + discover() 跳过点开头文件
- API 推送不表达删除：本地删掉的文件在远端残留 → 推送脚本显式同步删除
- conversation.json 的 JSON pointer 按**数组下标**硬编码，插入一条实验全体错位 → 改为按 id 查找
- GitHub secret scanning 会拦包含 token 的推送（连历史 blob 都算）→ token 只走环境变量

## 3. 驱动协议：全部假设与验证状态（复盘重点）

官方只给断言 schema（`.result` 是 JSON 数组），不给输出格式。我们实现并验证了 5 种封装，均可通过 20/20 官方用例：

| MVD_PROFILE | 输出形态 | 验证状态 |
|---|---|---|
| `text`（曾默认） | 查询=表头+tab行；DML=单行 `N row(s) affected`；**DDL/BEGIN/COMMIT=零输出** | 20/20（我们自己的 runner） |
| `json` | 每条语句一个 JSON 对象/行 | 20/20 |
| `jsonarray` | stdout 整体为**一个 JSON 数组**，元素与 `.result` 断言一一对应 | 20/20 |
| `echo` | mysqltest 经典回显形态 | 20/20 |
| `mysql` | 真 MySQL wire protocol（真实 mysql 客户端验证过） | 手工通过 |

### 3.1 关键推理：text 模式必然错位（第 4 次 0 分后的新发现）

text 模式下 7 条语句只产出 5 个响应：

```
CREATE TABLE d (...)   → (无输出!)
INSERT INTO d ...      → 1 row(s) affected
SELECT id FROM d       → id⇥1
BEGIN                  → (无输出!)
UPDATE ...             → ERROR...(或计数)
COMMIT                 → (无输出!)
SELECT ...             → id⇥z
```

**任何"按语句计数对齐输出"的驱动都会全部错位。** 而 `.result` 是与 SQL 一一对应的 JSON 数组 → **`jsonarray` 是唯一在"响应条数=语句条数"意义上自洽的格式**。

### 3.2 与官方断言对象的同构性（jsonarray 的依据）
```
我们输出                                    官方 .result
{}                                    ↔    {}
{"affected_rows": 1}                  ↔    {"affected_rows": 1}
{"error": "duplicate_key"}            ↔    {"error": "duplicate_key"}
{"columns":[...],"rows":[[1,5.0]]}    ↔    {"columns":[...],"rows":[[1,5.0]]}
```
浮点输出为 JSON number（`5.0`），与官方一致（文本协议无法区分 `5` 与 `5.0`）。
错误映射到语义名：1062→duplicate_key、1064/1235→unsupported_sql 等。

### 3.3 已排除的可能性
- 输入侧 JSON 请求（赛题明文否定）
- TCP/MySQL 网络连接（"不通过 TCP 端口连接选手程序"、"不启动网络监听服务"）
- 别人的公开实现可参考：GitHub 代码搜索 0 命中

## 6. 给其他队伍的可执行建议

1. **先跑环境预检**（免费）——它检查"启动、协议和公开样例"，是我们没走的一步棋
2. **不要信"本地测试全绿"**：用官方公开用例的**断言格式**反测自己的输出；再穷举样例没用的形态（多行、别名、引号向量、DESC、无 LIMIT、事务内检索…）

4. **性能只在正式规模+空闲机器上测**；每修一个优化立刻跑 recall + bench 双回归
5. **AI 全流程辅助是允许的**：conversation.json 的证据链要"学生贡献 + 实际结果"分离、指针可定位、无重复；我们用脚本从真实命令输出生成并用校验器验证
